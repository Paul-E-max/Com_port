General:
TEST_SEQUENCER provides a means to run a test script that will guide an operator through a sequence of tests.  It is formally known as TS014.  Generally, each test item is divided into title, instructions to an operator and commands that TS014 will execute.
If a script is given on the calling command line, and is accessible, it is automatically loaded and executed.  For example, place “DISCOVER\DISCOVER_TEST_PARC” in a short-cut at the end of its target field following TS014_TEST_SEQUENCER.exe



Abbreviations and common labels:

CR	Carriage Return
I2C	Inter-Integrated Circuit serial communications protocol
LF	Line Feed
PC	Personal Computer
RS232	Recommended Standard 232 serial communications protocol
USB	Universal Serial Bus

Directory structure:

Create the following directories around the TS014 application’s executable.  In the example below, one project has been listed here called “project”; of course, any number of projects might be created. 

EXE					// Executable files, typically BAT files
LIB					// Library subroutines common to many projects
project					// Directory with test scripts specific to this project
project \DISPLAYS			// JPG files referred to by the test scripts
project \LOGS					// Log files generated by running test scripts
project \NOTES					// Notes made by operator about a run or diagnostics process
project \SUBS					// Subroutines called by the test scrips
TEST_SEQUENCER_PROJECTS.TXT	// Summary of available projects, see CONNECT command
TEST_SEQUENCER_SNR_LIST.TXT	// Summary of serial numbers entered
TEST_SEQUENCER_USER.TXT		// Summary of current application parameters
TEST_SEQUENCER.exe			// TS014 application executable

Script Layout and Syntax:
Scripts should be created as plain text files.  File names should avoid spaces where possible and must have the extension “test”; for instance, SHORT_EXAMPLE_SCRIPT.test where under-score has been used in place of spaces.  A short example of a script is shown below:-

// - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -
// Filename:		SHORT_EXAMPLE_SCRIPT.test
// Project:		TEST_SEQUENCER
// PCB No.:		276-021-AS-02
// Author:      	Foster & Freeman Ltd - Chris Ashworth
// Modified:    	04.08.2022
//
// Description:	Demonstrates layout and syntax of a simple test procedure.
//
#1: Transit Bolts
SET: BOLT_COUNT = 2
Remove the %BOLT_COUNT% Transit bolts. Retain to re-fit later.
Display: T1.jpg
CLICK_OK:

#2: Cosmetic Damage
Check for cosmetic damage. Check for impact damage, and for rubbing during vibration.
PASS_FAIL:

#QUIT:
COMMAND: DISCOVER-Top BLACK
//
// End of file
// - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -

* Comments about the script are prefixed by “//”
* Lines beginning with a "#" signal the start of an individual test
* Lines following the start of a test are either commands or instructions to the operator
* Capitalized reserved words at the start of a line that are suffixed by a colon are commands
* Labels encapsulated by “%” are replaced by values typically assigned by the SET command
* Expressions encapsulated by “[“ and “]” are numerically evaluated
* Use “{“ or “}” characters for Bus Pirate and they are changed to “[“ or “]” during transmission 
* Test results are recorded in a log file
* And finally, #QUIT: is executed when the operator hits the QUIT button
Script Comments:
All characters following a double forward slash are assumed to be script comments and ignored for the purposes of script execution.  Liberal use of comments about the script will help to explain what the test is trying to achieve.  These are aimed at someone editing the script in the future.  Comments do not impede the scripts execution.


Test Labels:
Test labels are normally numeric and presented in ascending order.  Use a colon as a suffix to separate the test’s label from an optional title.  The combined label and title are displayed at the top of the form during the test’s execution and the other boxes are cleared in preparation for the new test.
For example,	#2: Cosmetic Damage		Begins test ‘2’

Non-numeric test labels such as #N2: do not update the title and do not clear the other boxes – they are assumed to be part of the same test, typically used for destinations of the GOTO command in more complicated tests or within a subroutine.
Instructions to the Operator:
Instructions are written in plain text without any specific syntax.  They are presented to the operator in a scrollable text box marked “Instructions:” and persist for the life of each test.  In figure 1, use the “Back” label next to “Instructions:” to review earlier entries where necessary.  Use “Next” to navigate forwards through these historic instructions.  Note that historic instructions are displayed in a different colour.  “OK” just below Back and Next returns to the current step of the current test.
Normally, blank lines are ignored, but a single ‘.’ at the beginning of the line forces a blank line to be display in the scrollable text box for the operator.  Prefix with a space to display a single full stop. 
Variable Labels:
Labels such as %A_LABEL% should have been initialised before use.  They are replaced with their assigned value before being used within instructions to the operator.
Predefined Labels:
Label 	Description
DELIMITER	Delimiter between VERIFY command and expected response (defaults to “###”)
FAILED	Current fail count as displayed at top of screen
INPUT		Last input provided by the operator
OPERATOR	The operator field provided by the operator
PASSED	Current pass count as displayed at top of screen
PCB_NO	PCB No. field, normally filled in by test script entry such as // PCB No.: 123-456
SERIAL_NO	Serial No. field filled in by operator
TEST_NAME	Test Filename field selected by the operator, note this cannot be modified by SET:
VERIFY		The generic expected response to VERIFY commands (if delimiter not used)
Predefined labels provide access to items on the control panel such as the PCB number and user input.  Use them in the same fashion as variable labels.
For example,	SET: PCB_NO = 270-369
		PCB No. is %PCB_NO%		// Would display “PCB No. is 270-369”


Expressions:
Expressions encapsulated between “[“ and “]” characters are numerically evaluated before use.  The resultant single number (without square brackets) can be used within instructions to the operator.  Note that this affects the last result; a non-zero being a PASS and zero a FAIL. Typical operators available are +, -, *, /, <, >, <=, >=, <>, = and % for modulus.  There are no bit wise operators.
The number of decimal places can be set using a single integer followed by “DP” within a set of square brackets.  This will evaluate expressions and display up to the number of decimal places defined by the given integer.  To force the use of a specific number of decimal places, use the suffix “FDP” instead of “DP”.  The default is three decimal places and discards trailing zeros.
For example,	SET: N = 3
		Place [%N% * 2] bolts in a box	// Would display “Place 6 bolts in a box”
		This [%N% - 3] is a FAIL result	// A following IF: would respond to this zero result
       [1DP]				// Set format to one decimal place
       Display value with 1dp [1.567]	// Evaluates expression and displays 1.6
       [2FDP]				// Set format to two fixed decimal places
       Display value with 2dp [1.5]	// Evaluates expression and displays 1.50


Screen Controls:
Test Filename:	Set the test to run, usually selected via Browse button.  Double click to edit script.  Hold Ctrl key down and double click to edit last log file.  Hold Shift key down and double click to edit this manual.
PCB No.:	This field is typically set by the test script header (as in // PCB No.: 279-027-PC-03) but can be set manually if necessary.
Browse:	Browse directories to select a test script.  Use Ctrl key and click browse button to start Explorer.exe in the current directory.  Use Shift key and click browse button to edit the project list.  
Operator initials:	Identify the operator using initials, use the drop-down to select previous entries.  
Serial No.:	Manually enter the serial number for each test item.  This could be filled in using the test script instruction INPUT: SERIAL_NO.
RUN/QUIT:	Runs or quits the currently selected test script.
INPUT:	Appears when operator input is required by the test script.
Log comments:	The operator may wish to add details to the log file as the test script progresses.
Add notes:	The operator may need to add notes on the running of a test script or the handling of common failures.
Quick notes:	Three frequently used expressions can be held and are injected into the comment field using a double click.  For example, “Test cannot be performed” or “Further investigation is required” can be typed into two of the Quick notes fields and the operator would add them to the log file by double clicking the required expression.
Light colours:	There is a chose between light coloured screen layout and a darker variety.
Big screen:	The operator may have to perform tasks upon hardware that results in the display monitor being at some distance and consequently difficult to read.  Use the Big screen option to increase the display size of the Test Sequencer application.  The default scale factor is 1.5, but this can be modified by right clicking the unticked Big screen check box.  At this point the operator can enter a different scale factor between 0.1 and 10.
Note that while the test is running, faint plus and minus symbols appear to the left of the Instructions text box.  The operator can use these to increase or decrease the font size; again, in the interest of improving the visibility of the relevant instructions.
Enable bell:	The application normally runs silently, tick this box to enable a bell on each error.
Images disabled:	Test scripts use images to guide the operator, particularly in the setup stage of each test.  If these are not required, they can be suppressed by ticking this check box.
PASS/FAIL:	Up to three buttons can be displayed below the Instructions text box and above the Visual information box.  These allow the operator to select the test result (PASS or FAIL), click OK or possibly RETRY to retry the test, depending upon the test scripts contents.


Commands and Parameters:
Commands control the function and flow of the tests.  Optional parameters follow the colon of a command and are separated by spaces.  For instance, “DISPLAY: T1.jpg” in the above script example.

Command Description:
CLICK_OK	Wait for operator to click the OK button
Displays a simple white OK button and waits for the operator to click it.  This normally follows a few lines of plain text to instruct the operator to perform a specific task.  Clicking the OK button allows the operator to signal to TS014 that the task has been performed.  An alternative button with the default label of SKIP in yellow can be displayed.  This is signalled by supplying a “#” label to jump to, should the button be pressed.  An alternative label can also be specified if SKIP is not appropriate.
For example,	CLICK_OK:		// Continues with the next test when OK is pressed
		CLICK_OK: #7		// Continues with test #7 if SKIP button pressed
		CLICK_OK: #3 Again	// Continues with test #3 if button marked “Again” is pressed

COMMAND	Send to a connected device the supplied command
Commands are directed at the connected device named by the first parameter.  The rest of the line is directed at this device.  This might be followed by the RESPONSE command to solicit an answer.  Note that any variables supplied within these commands are evaluated before being sent.
For example,	COMMAND: I2C WR 0	// The command “WR 0” is directed at the device “I2C”

COMMENT	Write to the “Comment:” text box, typically a prompt for operator input
The comment text box is where the operator enters details about the current test that need to be recorded within the test’s log file.  If a parameter is provided, it is placed in the comment box and may serve as a prompt to the operator and/or the reader of the log file.  Use the prefix “+” to append to existing comments and “\n” to insert a newline character.
For example,	COMMENT: Place notes here:	// Prompts operator to add a log file comment

CONNECT	Connects to the device specified by the supplied parameter
Devices connected to the PC as COM ports are scanned by opening each port in turn, issuing the appropriate identification command and checking for a valid response.  The parameter supplied should be one of the entries listed under ‘Project’ in the TEST_SEQUENCER_PROJECTS.TXT file.  If it is not found, then the connection will fail and can be tested using the IF, IF_NOT and ELSE commands.
For example,	CONNECT: DISCOVER		// Finds first device that responds with DISCOVER
		CONNECT: DISCOVER-top	// Finds specifically DISCOVER-top
		CONNECT: I2C			// Finds the Curiosity Nano device for I2C comms
		
DELAY	Wait a specified number of milliseconds
Many processes demand small delays to allow other events to complete before the test continues.  Although these delays are specified in milliseconds, note that this is only accurate to within plus or minus ten.
For example,	DELAY: 3000		// Pause for three seconds



DIAG	Add a line to diagnose a failing test
Adds the rest of the line to the diagnostics content.  If a failure is encountered, then the diagnostic content is saved in a DIAG file within the LOGS directory.  Next time this test script is selected, the DIAG file is detected and a red “FAILURES N” button appears where ‘N’ is the number of failures encountered.  Typically, a diagnostic line would describe the potential cause of the fault and/or potential remedies.  Clicking “FAILURES N” displays each failure in turn.  Use OK button to advance through the list during the review and the red FAIL button (at the top of the screen) to step backwards if required.  The DIAG record persist until the test is rerun with a PASS result to eliminate the previous recorded.

Diagnostic content is accumulated during the execution of each test, starting anew on each numeric test label.  A maximum of twenty lines per failure are permitted.  For complicated tests, CLEAR: can be used at the start of a diagnostics line to discard existing content and to start a fresh.
If the word DISPLAY: appears at the start of a diagnostics line, followed by a filename available in the DISPLAYS directory, then it is displayed as supporting information.  JPG and BMP files are displayed in the area reserved for images at the bottom of the screen.  TXT files are displayed as text in the middle of the screen and are more suitable for common faults that require a long explanation.
For example,	#4: New test clears out previous DIAG entries
		DIAG: Typical instance of a single line with a value = %variable%
		PASS_FAIL:		// Records the result in DIAG file
		DIAG: CLEAR:		// Next PASS_FAIL may require a different diagnoses
		DIAG: DISPLAY: info.txt
		DIAG: DISPLAY: image.jpg
		PASS_FAIL:		// and FAIL would record just the two above DIAG entries
	Holding Ctrl key when clicking “FAILURES N” button provides the option to delete a DIAG file.

DISCONNECT	Disconnects the device specified by the supplied parameter
Disconnect a device once it is no longer required.  There is a limit of ten devices that can be connected at any one time, so disconnecting once a device is finished with will maximise the available connection space.

DISPLAY	Place the supplied image file on display to provide visual information to the operator
Display the supplied JPG or BMP image that is stored in the DISPLAYS subdirectory – “A picture is worth a thousand words”.  Note that if the “Images disabled” is ticked, then the display is truncated to hide these images.
For example,	DISPLAY: T21.jpg	// Fetches DISPLAYS\T21.jpg and displays it
   
ELSE	Next test is given by the supplied parameter if last result was FAIL
If the last command (such as PASS_FAIL or RANGE) generated a FAIL, then proceed to the test label supplied as a parameter.  If no parameter is supplied, the following line is executed.
For example,	PASS_FAIL: 		// Operator clicks on either PASS or FAIL button
		IF:			// Indicates that a conditional statement follows
		GOTO: #12		// Go to test 12 if PASS button clicked
		ELSE: #14		// Else go to test 14 if FAIL button clicked

EXE	Execute a system command line
If an external application is required to complete a test, then EXE can be used to feed the supplied parameters to a DOS Command Prompt.  This Command Prompt opens within the EXE subdirectory to reduce the risk of just any old executable being started – this command should still be used with  caution!  It does not affect any previous PASS or FAIL result.
For example,	EXE: SETUP.bat 		// Will attempt to execute EXE\SETUP.bat

GOTO	Next test is given by the supplied parameter
Redirect the flow of Test Sequencer to the test step given by the supplied parameter.  This is an unconditional leap to a test label within the current script; as in the main script may be redirected to another test and a subroutine might be redirected to a test label within itself, but there is no means to leap from subroutine to main script or visa-versa.  Typically, this command follows an IF command to provide conditional flow control. 
For example,	IF: %TEMP% = 100	// Conditional statement follows based upon this result
		GOTO: #12		// Go to test 12 if variable TEMP equals 100
		ELSE: #14		// Else go to test 14

Note that if the target test step is numeric, the screen’s instructions and comments are cleared ready to start a wholly new test step.  However, if the target test step does not start with a digit, these fields are left untouched.  This is useful when a test requires a number of conditional steps to complete. 

GUI	Define Graphical User Interface controls

A graphical user interface is available as an alternative to the sequentially stepped execution mode normally employed by TS014.  Use GUI commands to define user controls such as buttons and text boxes, then switch the GUI mode on.  The user drives the process by clicking on the controls defined in the GUI area.  The normal sequential stepped execution is returned to by switching the GUI mode off.  See GUI Command Set: for more details.

IF	If last result is PASS or the optional expression is true (none-zero), perform next line
The IF command is used to conditionally execute the following line because a test passed.  Where no parameter is supplied the test result has already been evaluated in a previous line, typically using PASS_FAIL or RANGE.  Where a parameter is supplied, it is evaluated and the result used to conditionally execute the following line.  A none-zero result is a PASS and the following line is executed.  A zero result if a FAIL and the following line is skipped.  Note that string compare can be performed by using the STR_EQ operator.
For example,	PASS_FAIL: 		// Operator clicks on either PASS or FAIL button.
		IF:			// Indicates that a conditional statement follows.
		GOTO: #12		// Go to test 12 if PASS button clicked.
		IF: %TEMP% > 0		// If statement with a numeric operator.
		GOTO: #12		// Go to test 12 if variable TEMP is greater than zero
		IF: %T%  STR_EQ ?	// If statement with a string compare, true if equal.
		GOTO: #14		// Go to test 14 if variable T is equal to question mark

IF_NOT	If last result is FAIL or the optional expression is false (zero), perform next line
The IF_NOT command is used to conditionally execute the following line because a test failed.  Where no parameter is supplied the test result has already been evaluated in a previous line, typically using PASS_FAIL or RANGE.  Where a parameter is supplied, it is evaluated and the result used to conditionally execute the following line.  A none-zero result is a PASS and the following line is skipped.  A zero result if a FAIL and the following line is executed.  Note that string compares can be performed by using the comparator STR_EQ.
For example,	PASS_FAIL: 		// Operator clicks on either PASS or FAIL button.
		IF_NOT:			// Indicates that a conditional statement follows.
		GOTO: #12		// Go to test 12 if FAIL button clicked.
		IF_NOT: %TEMP% > 0	// If not statement with a numeric operator.
		GOTO: #12		// Go to test 12 if variable TEMP is not greater than zero
		IF_NOT: %T%  STR_EQ ?	// If not statement with a string compare, true if not equal.
		GOTO: #14		// Go to test 14 if variable T is not equal to question mark

IMPORTANT	Displays the supplied parameter in a dedicated text box
For important messages that really do need to grab the attention of the operator, use this command to display a message in red ink and place it in a text box of its own that appears below the usual instructions together with a label of “IMPORTANT”.   Without a parameter, this command removes- any existing IMPORTANT message.
For example,	#19: Hold
       Z-axis release test
       IMPORTANT: Hold on to the docking head – it may move up when . . . etc.
       CLICK_OK:


Figure 2 - Example of IMPORTANT notes as seen by the test operator

INPUT	Display the input field and wait for operate to enter information
The operator many need to enter a parameter that is accessible in the script.  The INPUT command displays a dedicated field and waits for the operator to enter the required parameter.  If the command is followed by any text, the first word is taken to be the label for the parameter to be loaded and an optional second word provides a default value.  If no parameters are supplied, then the input is accessible using %INPUT% and the prompt next to the input will simply read “parameter”.  Either ENTER key or the OK button will accept the input as complete.
For example,	Enter a delay		// Suitable prompt to the operator
       INPUT: delay 5000	// Displays the INPUT field and provides a default value
       DELAY: %delay%	// Execute a command using the operator’s input
       INPUT: SERIAL_NO	// Get operator to update Serial No. field

Note that function, arrow and paging keys generate equivalent text and an auto-ENTER.  The text output will be F1-F12, Up, Down, Left, Right, PageUp, PageDown, Home and End.

INT	Set the label given by the first parameter to the integer given by rest of the line
The normal syntax for integer assignment is label equals expression.  The delimiter ‘=’ between label and expression is optional, but useful to improve readability.  Labels are single strings of characters A-Z, 0-9 and underscore.  The expression can include predefined variables which permit obscure numbers and strings to be presented as meaningful named entities.  They can also be used to generalise a process such that each individual variable can be assigned during an initial stage and then used in multiple instances later in the test process.  Note that square brackets are used to evaluate simple arithmetic expressions.  
For example,	INT: DEC = 122.9		// The variable DEC will be set to 122
		INT: ROUNDUP = [122.9 + 0.5]	// The variable ROUNDUP will be set to 123

LIB	Execute a library routine specified by the first parameter
For frequently used procedures, call a library item by name.  The extension of “test” is assumed, and it needs to be stored in the LIB subdirectory within the same directory as TEST_SEQUENCER.exe
For example,	#2: Cosmetic Damage	// Typical start of a product test procedure
		LIB: COSMETIC		// Continues at the start of LIB\COSMETIC.test

The file: LIB\COSMETIC.test consists of . . .

		Check for:		// Four lines of instruction to guide the operator
1) Cosmetic damage
2) Impact damage
3) Rubbing during vibration
PASS_FAIL:		// Wait for operator to answer PASS or FAIL
//
RETURN:

PASS_FAIL	Wait for operator to click on PASS or FAIL buttons
Displays a green PASS button and red FAIL button, then waits for the operate to click one.  This normally follows a few lines of plain text to question the operator about a specific aspect of a test.  Clicking the PASS button records in the log file that the test passed and similarly, clicking FAIL records that result instead.  The result recorded is accompanied by the test label and a line of text describing the test performed.  An alternative button with the default label of RETRY in yellow can be displayed.  This is signalled by supplying a “#” label to jump to, should the button be pressed.  An alternative label can also be specified if RETRY is not appropriate.
For example,	Check for scratches	// Typical prompt to the operator to inspect something
		PASS_FAIL:		// Continues with the next test when PASS or FAIL is pressed
		PASS_FAIL: #7		// Alternatively, put up a yellow button marked RETRY
		
       PASS_FAIL: #3 Repeat	// Similarly, put up a white button marked “Repeat” instead
See SKIP_FAIL command to wait for operator to click SKIP or FAIL buttons.
RANGE	Check first parameter is in range of second plus or minus the third
Perform a test on the first parameter to check that it is within a valid range.  The range is centred on the second parameter.  The third parameter indicates the range around the centre value that is permissible.  If the third parameter is suffixed by “%” (other than a character that denotes a variable to be evaluated), then the range is a percentage of the centre value.  A PASS is logged if the first parameter is within range, otherwise a FAIL is logged.  Trailing non-numeric characters are ignored.
For example,	RANGE: %TEMP%  80  5		// PASS if TEMP is between 75 and 85

READ		Wait for device to respond and save as named variables 

Wait for the named device to reply and place the space delimited values read into the named variables.  The name of the device to be read should correspond to one already connected.  The operator may hit the SKIP button if the process is locked-up.  Variables not read are left unchanged.
For example,	READ: I2C LOW HIGH		// Read two bytes into variables LOW and HIGH

READFOR	Read waits for a limited period (ms) before abandoning the process 

READ, READLINE and RESPONSE all wait for their required inputs to arrive, allowing the operator to hit the SKIP button if the process is locked-up.  However, if READFOR is set to a non-zero value, the process is abandoned after that many milliseconds.  The default setting is zero and therefore wait until a response arrives or the operator hits SKIP.  Note that the period is to the nearest 50ms.
For example,	READFOR: 95			// Reads wait up to 100ms before abandoning process
       READ: I2C LOW HIGH		// Read these two bytes within 100ms

READLINE	Wait for device to respond and save whole line as a named variable 

Wait for the named device to reply and place the whole line (all characters up to the newline character) into the named variable.  The name of the device to be read should correspond to one already connected.  The operator may hit the SKIP button if the process is locked-up, in which case the variable is left unchanged.
For example,	READLINE: I2C WHOLE_LINE	// Read the whole line into the variable WHOLE_LINE

RESPONSE	Wait for device to respond or the FAIL button to be hit and check response
Wait for the named device to reply and check to see if the response starts with the given string.  If the response matches, the result is a PASS; if not, the result is a FAIL.  This result is logged together with the test label, title and up to one line of any instruction presented to the operator.  The name of the device to be read should correspond to one already connected.  The operator may hit the FAIL button if the process is locked-up.
For example,	RESPONSE: DISCOVER #3	// DISCOVER returns #3 if a solenoid button is pressed

RETURN	Exit a subroutine
Exit a subroutine, typically placed at the end of the file.  A subroutine assumes that it is to return when it hits the end of the file, so this application of the command is more about being consistent than necessity.  However, it might be necessary to break out of a subroutine early, for instance when an error condition is meet.

SAVE_LOG	Saves summary of test to the log file (optional)
Typically, SAVE_LOG would be the last command in a script file and therefore part of the #QUIT: section.  It records the over-all result of a test and closes the log file.  If the serial number field is filled in, the filename of the log will be suffixed by the value provided.  Should end of file be encountered without a SAVE_LOG, then the over-all result is force out by default before the log file is closed, hence the mention of “optional” in the command title.
Note that if any further commands are executed outside of the #QUIT: section, this will start a new log file with the current date and time stamp.

SET	Set the label given by the first parameter to expression given by rest of the line
The normal syntax for assignment is label equals expression.  The delimiter ‘=’ between label and expression is optional, but useful to improve readability.  Labels are single strings of characters A-Z, 0-9 and underscore.  The expression can include predefined variables which permit obscure numbers and strings to be presented as meaningful named entities.  They can also be used to generalise a process such that each individual variable can be assigned during an initial stage and then used in multiple instances later in the test process.  Note that square brackets are used to evaluate simple arithmetic expressions that may include hexadecimals prefixed by “0x” or binaries prefixed by “0b”.  
For example,	SET: DEC = 122			// The value DEC will be set to 122
		SET: NEXT = [%DEC% + 1]	// The value NEXT will be set to 123
		SET: HEX = [0x7A]		// The value HEX will be set to the decimal value 122
		SET: STR = string of characters	// The value STR is set to “string of characters”


SKIP_FAIL	Wait for operator to click on SKIP or FAIL buttons
Displays an orange SKIP button and red FAIL button, then waits for the operate to click one.  This normally follows a few lines of plain text to question the operator about a specific aspect of a test.  Clicking the SKIP button records in the log file that the test has been skipped without incrementing the pass count, whereas clicking FAIL records that result instead.  The result recorded is accompanied by the test label and a line of text describing the test performed.  An alternative button with the default label of RETRY in yellow can be displayed.  This is signalled by supplying a “#” label to jump to, should the button be pressed.  An alternative label can also be specified if RETRY is not appropriate.
For example,	Check for scratches	// Typical prompt to the operator to inspect something
		SKIP_FAIL:		// Continues with the next test when SKIP or FAIL is pressed
       SKIP_FAIL: #7		// Alternatively, put up a yellow button marked RETRY
       SKIP_FAIL: #3 Repeat	// Similarly, put up a white button marked “Repeat” instead

SUB	Execute a subroutine specified by the first parameter
Create a named procedure and call it as a subroutine.  The extension of “test” is assumed, and it needs to be stored in the SUB subdirectory within the same directory as the script file.  The subroutine should ideally end with a RETURN command.
For example,	#8: Check temperature		// Typical item to test
		SUB: CHECK_TEMP		// A common activity worthy of a name
		
The file: SUB\CHECK_TEMP.test in the same directory as the script might consists of . . .

       COMMAND: I2C ADDR 0x60	// Assume it has already been connected
       COMMAND: I2C WR 8		// Points to an I2C register to be read
       COMMAND: I2C RD 2		// Ask the device to send two bytes
       READ:  I2C  LOW  HIGH		// Read two bytes into handy variables
SET: TEMP = [%LOW%+256*%HIGH%]
//
// Following “Check that . . .” fleetingly shows up on screen, but its main purpose is to
// appear in the log file alongside the PASS or FAIL statement to show context.
//
Check that the temperature is between 78 and 82 degrees C
RANGE:  %TEMP%  80  2		// Generates a PASS if between 78 and 82 else FAIL
//
RETURN:

TEST	Increment passed or failed test count
Most tests require the operator to click either PASS or FAIL buttons to continue.  For tests that can be performed without the operator’s input, this command allows the script to increment either the ‘Passed’ or ‘Failed’ counters.  It also records the result in the log file.  Use a parameter of PASSED to increment the ‘Passed’ count.  Use a parameter of FAILED to increment the ‘Failed’ count.  Use a parameter of NOTE to include a message in the log file.  Any additional comments that follow the PASSED/FAILED/NOTE parameter are included in the log file output.  If no parameters are supplied, then the last condition is taken as a pass or failure.
For example,	TEST: PASSED			// To increment the ‘Passed’ count
		TEST: FAILED with comment	// Increments fail count and adds comment in log file
		TEST: NOTE comment logged	// Just adds this comment to the log file
		This set condition to pass [1]	// Setup pass or failure state . . .
		TEST:				// . . . and this will increment the ‘Passed’ count

UNSET	The given label is destroyed
There is limited space in which to store labels and being an interpreted process (as in each line is examined and executed one at a time) the more labels there are the more time it can take to process them all.  For these reasons, it can be useful to destroy redundant variables.
For example,	UNSET: TEMP			// To drop the variable TEMP

VERIFY		Verify command sent to connected device responds with value in variable VERIFY
Verify that the given command line, when sent to previously connected device, responds with the contents of the variable VERIFY.  A log is made of the PASS/FAIL state, the command line and the response.  An alternative method of specifying the expected response is to include an instance of the “###” delimiter within the given command line, then the command sent proceeds this and the expected response follows it.  Note that it is important that a connection is first established before trying to use this command and that the default delimiter can be modified by setting the value of predefined variable DELIMITER.  Should the response only need to start with the expected response, then it should be suffixed with “…”.
For example,	CONNECT: MVC_FFLEX		// Connect to an available device
		SET: VERIFY = 0 7 87AA		// Setup the correct response
		VERIFY: FAKE			// This should register a failure
		VERIFY: FAKE CLEAR		// This should register a pass
		VERIFY: FAKE OFF ### 0 7 87AA	// Note the use of the delimiter
		SET: DELIMITER = >>		// Setting the VERIFY delimiter to some alternative
		VERIFY: FAKE OFF >> 0 7 87AA	// The alternative delimiter in use
		VERIFY: VERSION >> 0 …		// Check the response starts with a zero

A graphical user interface is available as an alternative to the sequentially stepped execution mode normally employed by TS014.  Use GUI commands to define user controls such as buttons and text boxes, then switch the GUI mode on.  The user drives the process by clicking on the controls defined in the GUI area.  The normal sequential stepped execution is returned by switching the GUI mode off.

Graphical Items:
AREA	Define the GUI area
Define the GUI area as left, top, width and height in screen units scaled by big screen if selected.  Zero, zero is the top left of TS014, just below the title bar, and extends to the right and down the screen as the parameters increase in value.   The default is a dark grey area covering the whole section below the RUN button.  
For example,	GUI: Black AREA 0 0 100 50 // Half the screen is made available as GUI area in black

BUTTON	Creates a button to execute a step
The button is created with an optional label supplied in quotes.  When clicked by the user, the button executes a script step defined by the next parameter, this must be present and prefixed by a hash.  Optional position and size follow, which define the button’s left, top corner, its width and its height.  If position or size are not defined, the next available space is used and the last button size is used.  If a label is not supplied, the script step is used by default with the hash character removed.
For example,	GUI: BUTTON “Just do it” #2 20 60 // Reasonable size grey button created at top left
		GUI: BUTTON #SHIFT // A grey button is created below the above item labelled SHIFT

CLEAR	Clear the GUI area
All items defined by any previous GUI commands are removed.  The background colour and area defined are retained.  Use GUI: MODE off to remove the GUI area altogether.

INPUT	Creates a white text box for the user to enter a named parameter
While the GUI area is displayed, the INPUT items allow the user to specify the value of a named value.  The name should not include the % character at the beginning or end.  Later in the script, this can be used in the normal way, but with the %XYZ% syntax.  Following the name of the value, define left, top corner, width and height.  If the name is missed, it defaults to INPUT.
For example,	GUI: INPUT COUNT 0 50 // Put up an input box with label COUNT: at 0, 50
		GUI: TEXT “COUNT = %COUNT%” // . . . and display what the user entered

MODE	Switch the GUI mode to ON, MIN, MAX or OFF
Once the GUI controls have been defined, switch them on and change from the sequential stepped mode to the user driven mode.  The script is effectively halted at this point until the user clicks on a button that transfers control momentarily to a defined test section.  Once the end of the test section has been reached, control is again suspended, waiting for the user’s actions.  MIN or MAX act the same as ON but also specify the way in which the GUI is to be displayed.  MIN minimises the application area to exactly encompass the area in use.  MAX maximises the application to the whole screen.  To return to the sequential stepped mode, switch the GUI mode off or quit the script altogether.
For example,	GUI: MODE ON // Enables the interactive graphical mode

OUTPUT	Define a light-yellow text box to display the value of a variable in
Define a text box for the purpose of displaying a named variable.  The name should not include the % character at the beginning or end.  Following the name of the value, define left, top corner, width and height.  If the name is missed, it defaults to OUTPUT.
For example,	GUI: OUTPUT RESULT 100 50 200 // Display the RESULT: in a wide box

TEXT	Define text box without border or background
Define a transparent area to display optional text supplied in quotes.  The following parameters are left, top, width and height.  Any optional colour prefix refers to the text.
For example,	GUI: TEXT “Some text” 0 10 100 5 // Text box with no infill that spans the screen

TEXTBOX	Define a coloured text box area with a border
Define a coloured area to display some optional text supplied in quotes.  The next parameters are left, top, width and height.  Any optional colour prefix refers to the background of the text.
For example,	GUI: Pink TEXTBOX 2 10 25 5 // Text box with pink infill
		GUI: Red // Text will be red.
		Some text to display // Any following script text ends up in the above GUI text box


Removing an item:
To remove an item, define it again with the colour prefix of Remove.  It is only necessary to provide the item type and its starting.
For example,	GUI: Yellow TEXT “Some text” 5 5 25 10 // Some yellow text without a box at the top
	DELAY: 3000
 	GUI: Remove TEXT 5 5 // Blanks out the text at the top of the screen

TXT files in the NOTES directory:
The operator may use the “Add notes” button during either the running of a test or during the diagnostics of run failures.  The effect of this is to record these notes and present them to the operator when the test is later rerun; the hope being that these notes will help the next operator to run the test or diagnose a fault. 

These notes files reside in the NOTES directory and will have the same filename as the test that was being run, but with a TXT extension rather than TEST.  The following is an example of the sort of thing that might end up in such a file.

#1: Run
Do ensure that TE019 is not plugged into the PC !
#2: Run
Pay particular attention to the picture below, some of the connectors are rather difficult to observe.
#1: Diag
Check on the devices that are plugged into the PC.
Some devices have been known to confuse this test.
#4: Diag
STOP - Please report this fault to PG.



Pseudo binary scripts:
There are instances where TEST scripts need to be supplied to third parties that should not be given access to the command set within this document.  To hide these, scripts can be encoded into a pseudo binary format.  This is done by setting the Operator field to FF_BIN which then reveals a black button ‘BIN’.  Pressing this black button saves an encoded form of the current script with the suffix “_BIN”.  Any file with this suffix is assumed to be encoded and is decoded before being run.  For this reason, test script filenames should not end in “_BIN”.
